# Authenticated owned browser SETUP preparation

## Goal

Replace the hand-written browser SETUP producer in the hosted failed-renewal fixture with an explicitly constructed server adapter: original authenticated reservation → one original SetupIntent create → real typed ACK → unbound setup proof. This is the next bounded connection to the verified browser permission flow, not a native launcher or a second payment attempt.

Baseline `87effaa8cc0b8b47417f9a3003a1028b9233055a` passed [full CI](https://github.com/viktar-mar/payment/actions/runs/42379983006): 5,366 backend cases, zero failures/errors, one existing skip, including all 76 failed-renewal composition cases. SDK/type/build, frontend, infrastructure and both runtime packaging checks passed. [Dedicated renewal CI](https://github.com/viktar-mar/payment/actions/runs/42379982986) passed. The prior browser preparation is verified in hosted composition; native failed renewal/method/recovery and full5B acceptance remain unverified.

## One original provider command

Public constructor takes method service, ProviderOperationStore, SubscriptionBillingProofStore, StripeCredentialResolver, StripeClientFactory, DigestPort and UTC Clock. Public `prepare(Reservation, SubscriptionCommandContext)` returns only the actual unbound `SubscriptionBillingProofStore.Setup`.

At entry authenticate the context; refuse any preexisting setup proof or provider step at the original `operation.providerOperationKey()+":SETUP"`, regardless of status. There is no ACK reuse, UNKNOWN replacement or lease takeover path. Reserve using only reserveOwnedFailedRenewalMethodStep(account,reservation,SETUP_INTENT_CREATE), independently verify the existing fingerprint contract, require fresh RESERVED/v0/no firstDispatchedAt, and claim once with a fresh claimant and the existing 60-second lease. Require first DISPATCHING/v1 and exact owner/key/fingerprint/account/resource identity. A losing concurrent claimant or any refusal before acquired ownership must not stop the winner.

If two fresh invocations both saw no row, either may win the single first claim even if its concurrent insert lost. The current reserve API returns one shared RESERVED row, not an insertion-ownership receipt. Ownership begins only at the successful first DISPATCHING/v1 claim. No store insertion-ownership API or additional dispatch budget is added.

Reuse StripeRequestFingerprint with the exact current SETUP_INTENT_CREATE_V1 fields and encoding already used by StripeBillingOwnership and owned_method_step_fingerprint; no new digest format or copied canonical encoder. Reinspect fresh context and require full equality after reservation/claim and immediately before SDK dispatch. Authorize setup through the existing proof API, requireOwnedFailedRenewalMethodDispatch and ProviderOperationGuard. No persistence transaction or lock may be held across SDK I/O; all inspections/steps/proof calls remain on the caller thread.

Execute one logical SDK `setupIntents.create` only. Exact request: original binding customer, OFF_SESSION usage, CARD allowed type, metadata account_id/site_id/customer_id/subscription_id/operation_id, and original :SETUP idempotency key. Pin existing API `2026-09-30.endive`, zero SDK/application retries, explicit connect/read limits at most two seconds and a complete-call worker limit of at most two seconds or remaining allowance. Bound the invocation by an immutable entry UTC+30s deadline, actual/injected monotonic 30s and original claim lease; recheck after blocking caller work before dispatch and acceptance. Cancel the worker on completion/failure/interruption, preserve caller interrupt. Do not add probes, GETs, account verification requests, confirmation, polling or fallback. The contract is one SDK command with zero application/SDK retries; no new physical-wire guarantee or transport change is introduced.

Database waits may delay the caller's return; they cannot extend dispatch or evidence-acceptance authority. This is not a promise to interrupt arbitrary JDBC work at 30 seconds. Ownership for terminal cleanup begins only after validating the acquired claim as the exact original first DISPATCHING/v1 claim with this fresh claimant; a malformed/foreign/second claim is not permission to stop someone else's branch.

Validate the actual returned SetupIntent with the unchanged package-local requireSetupRemote validator. Additionally require requires_payment_method, no attached payment method, and all five exact request metadata identities. Revalidate full context and the typed original claim on the caller before acknowledging. Persist the real original SDK ID through existing acknowledge, then revalidate before existing recordSetup. Return only its matching original operation/account/subscription/step/reference and null method. No client secret is read, returned, logged or persisted by this adapter; later secret issuance belongs only to the already reviewed browser issuer/reader.

ACK and proof use the existing independent short transactions; they are not claimed as one atomic transaction. An ACK may remain if proof persistence fails. Such a failure stops the owned branch and never grants a second POST or fills the proof via retry. Once the valid proof commit succeeds, return it without an extra post-commit clock/deadline failure. Client permission, binding and method completion remain separate and unchanged.

That final return also covers session revocation/expiry after the last successful pre-proof inspection while proof persistence waits or commits. The already dispatched original command may finish its non-secret, unbound receipt using the existing SQL gates; this confers no browser or method authority. Subsequent issuance/selection/consumption must still reject the revoked/expired original session. Revocation detected by any required inspection before that point refuses and stops the claim holder. Business/operation/stop drift still must pass the actual proof insertion guards; no relaxation of those guards is permitted. Cover both sides of this boundary in pure and genuine hosted tests instead of claiming the two existing independent transactions revalidate enrollment atomically.

After acquiring the original first claim, any context/dispatch/SDK/validation/ACK/proof failure is terminal: conservatively preserve uncertainty, stop the branch once through the existing method service after transactions unwind, and expose only a fixed source-owned unavailable error with no raw provider/cause text. Mark the owned original step UNKNOWN only where it is still the same DISPATCHING claim and cannot be an acknowledged receipt; never downgrade ACK. A failed stop/unknown update stays uncertain and grants no replacement or retry. Tests must distinguish pre-claim loser refusal from holder failure. These are original owned-command cleanup effects, not old-operation adoption.
