# Owned method and debt-recovery reads

## Intent

Prepare the next offline Stage 5B boundary: verify a newly saved card/customer graph while the original renewal debt remains unpaid, and describe a later full payment of that exact debt. Use Java, the existing hexagonal backend and the official cached Stripe SDK with inert transport tests. These readers supply descriptive evidence, never authorization or payment commands.

## Scope and decisions

Implement two package-private entry points in the existing Billing mapper, sharing its complete invoice/cash normalization. Accept the actual local PAST_DUE/debt projection; never fabricate an ACTIVE prestate to reuse the first-successful-renewal lane. Preserve existing ordinary, initial, successful-renewal and failed-renewal contracts. No registration, migrations, HTTP routes, launchers, financial writes or new dependencies.

Both reads require an exact supplied failed Admission/Failure join, owned Sandbox account/customer binding, original catalog and initial receipt, current PAST_DUE projection with the same bill, debt period, grace deadline, paidThrough, failure revision and original entitlement. They require exactly the original initial invoice and saved renewal invoice, original initial allocation/PI, and existing strict item/period/price/tax/adjustment/cash/reverse-allocation validation. Observation must be no earlier than the failure receipt. All SDK calls use the supplied existing ReadExecutor and its options on one shared Read instance; retain max100 requests, max10 pages of at most10 items each. The executor is required, not a default unbounded network fallback. The caller must separately authenticate durable records, readiness, deadlines and fences. A supplied record is not authority.

### Method read

Input is the supplied exact failed context plus a candidate containing a local SETUP operation, SubscriptionBillingProofStore.Setup, acknowledged SETUP_INTENT_CREATE step and acknowledged SUBSCRIPTION_UPDATE :METHOD step, and the existing DigestPort for fingerprints. The candidate represents pending local fact completion (PROCESSING), not a synthetic SUCCEEDED operation. Check same account/site/customer/subscription, expected failure revision, original policy, operation/key/reference and exact setup/method fingerprints, provider-step account/credential/resource/kind/status/key/reference, and Setup joins. Follow the existing setup fingerprint and remote metadata/creation-window/card/off_session rules rather than inventing a new provider contract.

SETUP creation must be no earlier than the failure receipt; its updatedAt must be no earlier than creation and no later than observation. Available provider-step dispatch/retry/order fields must be consistent with the operation and observation. ProviderOperation has no creation/acknowledgement timestamps, so this reader must not claim to authenticate those absent timestamps or native completion provenance. Read the strict unchanged failed-renewal graph, then the exact succeeded SetupIntent and PaymentMethod. Require SetupIntent customer/method to match the saved proof, non-live card/off_session shape and exact operation/subscription metadata; card attached to the original customer; subscription default method equal to that card. Keep renewal OPEN, saved default allocation and declined PI, no new cash and no paid-through/access extension. Return only snapshot, SetupIntent and method references. No client secret, card details, operation marker or completion authority is returned. Candidate receipt consistency is verified but persistence and native completion provenance are not authenticated by this mapper.

### Recovered read

Input adds a supplied Recovery and exact RESERVED RECOVER operation associated with the same failure bill/invoice/allocation/PI, revision and version. Require observation>=recovery association>=failure receipt, plus exact supplied admission/failure/recovery IDs/invoice/period before IO. Check owner scope, kind/status, operation key, authority scope and the existing owned recovery fingerprint formula. Require ACTIVE remote subscription but still use the actual local debt prestate. The original two invoices are CASH, each fully paid via its exact saved allocation/PI; reject replacement/split/zero/noncash/refunded/foreign/adjusted graphs. The recovered PI/Charge may differ in charge from the historical decline, but PI and allocation cannot change. Require one default renewal allocation, full requested/paid amounts, successful PI/Charge and exact reverse allocation. Return only snapshot/allocation/PI, without APPLIED marker or operationKey. A separate authenticated consumer is required before existing publishRecovery can apply it; do not turn supplied Recovery records into authorization.

## Explicit blockers retained

The ordinary Billing ownership path rejects clock-owned customers. The isolated fact gate rejects SETUP, and completing any Stripe fact consumes observationSequence. V34's failure-current proof requires the exact original failure sequence. Therefore a genuine method completion needs a separately designed append-only authenticated transition binding the failure prestate, one exact SETUP/provider receipt chain, and a permitted successor fence. Neither a saved method field nor an acknowledged update supplies that transition. This preparation must not relax V34, mark SETUP complete, reserve RECOVER, publish facts or claim end-to-end recovery works.

Native exact-owner time/readiness, contextual recovered-read publication, method transition authorization, runtime integration and delivered callbacks remain unimplemented acceptance boundaries. Native field/time interoperability remains NOT_RUN; Stage 5B remains NOT_ACCEPTED.

## Verification and execution limits

Tests use the existing socket-free official SDK fixture, real normalization and coherent positive graphs plus meaningful negative mutations. Verify exact GET-only request paths and option forwarding, no output secrets, local/context refusal before IO, cross-customer/method/setup/step/operation drift, unchanged debt, same recovered bill/allocation/PI, status/amount/tax/refund/reverse errors and paging limits. Run selected pure mapper/observer/service/fact regressions via fresh current-source javac/JUnit and cached dependencies. No local default test discovery, Spring/SQL contexts, Docker, Sandbox, provider account calls, Python, installation, old operation/DISPATCHING/key/archive access. All edits use apply_patch.

Subagents implement sequentially, each task gets independent review, followed by whole-change review. Root owns Git and publication. Preserve reports/worktree. Standing user Git/CI authorization permits publication after local review, with fresh synthetic hosted CI only; no local/native execution follows it.
