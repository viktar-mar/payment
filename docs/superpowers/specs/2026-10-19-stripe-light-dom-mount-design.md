# Stripe Element: совместимый монтаж и диагностика

## Основание и границы

Пользователь разрешил исправить монтаж Stripe Element для обычных оплат и донатов и связанную диагностику, с субагентами, тестами и независимым ревью. Sandbox пока не запускать. Работа остаётся в существующем worktree `codex/stripe-sandbox-5a`, основная папка/main не меняется. Этот документ описывает выбранный разработчиком способ реализации, а не дополнительные решения, якобы принятые пользователем; реализация начинается после подтверждения плана.

Офлайн-разбор локализовал несовместимость: Catalog и Donation помещают providerHost внутрь ShadowRoot, а ветка допуска текущего публичного Stripe.js `endive` такую структуру отвергает. Само наличие iframe и возврат public mount не доказывают ready. Исправление не является доказательством исчезновения реального Sandbox-таймаута.

## Требуемый результат

Stripe-контейнер обоих виджетов должен находиться в Light DOM того же документа и отображаться в прежнем месте виджета через именованный slot. Внешняя Shadow DOM-оболочка, оформление, темы, локаль, кнопки и публичный API сохраняются. У Fake сохраняется прежний путь монтажа. Нельзя подделывать ready, автоматически подтверждать оплату или расширять полномочия диагностических сценариев.

Provider-контейнер принадлежит конкретному виджету и конкретному поколению монтажа. Он не выбирается через глобальный CSS-поиск, публичный DOM-атрибут, похожий чужой элемент или доступный для подмены callback. Создание/поиск/закрытие своего контейнера централизованы в небольшом внутреннем SDK-модуле. Закрытие старого поколения не удаляет новый или чужой DOM. Замена/удаление host, slot или wrapper не должна превращаться в положительную диагностическую привязку; обнаруженная утрата остаётся окончательной. Быстрый detach/reinsert своих узлов также не должен возобновлять утраченную диагностическую сессию.

Собственный виджет, помещённый внутрь стороннего ShadowRoot, всё равно не даёт Stripe документный Light DOM. Предлагаемый ограниченный вариант не добавляет глобальных portals: он явно и безопасно отклоняет такой Stripe-монтаж до выдачи новой provider-capability. Fake не получает этого ограничения. Поддержка произвольных вложенных ShadowRoot через portal — отдельное изменение, не скрытая часть этого исправления.

## Диагностика и безопасность

SDK binding, manual/automatic snapshots и ручной наблюдатель геометрии/visibility/load используют только текущий внутренний owned providerHost. Pay остаётся в Shadow DOM. Должны сохраниться конечные схемы, provenance BROWSER_REPORTED, original60s observation, original15min authority, original cleanup ceiling, одноразовая выдача сессии и immutable deny подтверждения даже после закрытия/утраты наблюдателя.

Не добавлять чтение секретов/env/приватных логов, iframe URL/contents, resource timing, DevTools/HAR/console capture, сетевые попытки Stripe, новые backend/API операции, автоматические повторы или новые зависимости. Нельзя ослаблять CSP через unsafe-inline/unsafe-eval/широкие origins. По возможности сохранить существующие shadow stylesheet bytes/hash через wrapper; если контролируемые CSS bytes всё-таки изменятся, пересчитать только точные собственные hashes в nginx и gateway и проверить их потребителя.

## Проверка

Регрессия должна падать на прежнем размещении providerHost и проходить после исправления. Проверяется реальный SDK и реальный DOM-контейнер на границе mount; заглушка Stripe не может бесконтрольно принять ShadowRoot. Дополнительно нужен изолированный native Chromium-тест с перехватом всей сети на искусственных данных, проверяющий документный контейнер, slot-проекцию и cleanup у обоих виджетов. Его результат — совместимость DOM-контракта, не реальный Stripe ready.

Проверить оба виджета, независимость нескольких экземпляров, темы/локаль без перемонтажа, Fake, отключение/замену/повторное присоединение, retired lease, поддельные похожие узлы, пересоздание после cleanup, binding-loss, deny после close/loss, конечные отчёты, ручные/автоматические entries, Vite graph и isolated Docker COPY filesystem без запуска Docker. После каждой задачи — отдельное review spec+quality, затем финальный обзор всех изменений этого исправления.

Отдельный Sandbox-запуск требует нового явного разрешения после реализации и офлайн-проверок. До этого не утверждать, что реальные поля карты уже отрисовались.
